# ADR-017: Typed responsibility and project claims for M1

- Date: 2026-09-14
- Status: **PROPOSED — IMPLEMENTATION CLEARED BY INDEPENDENT REVIEW**
- Decision owner: supervising engineer; independent review must be recorded in `../reviews/`.

## Context

M1 curation requires supported responsibility bullets and client/open-source
projects to survive the same profile, plan, renderer and snapshot boundaries as
employment facts. The current schema stores only an optional unstructured
`EmploymentFact.description`; `compile_baseline` drops it, and no profile fact
can express a project, employment relationship or project-specific scope.
`build_pdf` also validates without the support-capture map. This permits a
synthetic profile to pass existing employment and snapshot fixtures while
silently omitting the claims M1 must preserve.

## Alternatives

1. Keep descriptions as opaque employment text. Rejected: it cannot bind each
   bullet or project to a subject, role, dates and evidence.
2. Encode projects as employment facts. Rejected: it misclassifies clients and
   creates duplicate employment entries.
3. Add typed revisioned responsibility and project records, exact approved
   variants and scoped support bindings, then thread captures through every
   validating boundary. Proposed.

## Proposed decision

Introduce bounded `ResponsibilityFact` and `ProjectFact` records. Each record
inherits a stable ID, revision, status, nonempty evidence references,
support-binding references and hash-bound approval. A responsibility carries an
exact revision-bound `FactRef` to an approved employment fact; its subject must
match that employment's subject and its wording variant must scope to that
responsibility/employment pair. A project carries a stable project entity,
optional exact revision-bound employment `FactRef`, subject, role and typed
period (including unknown dates). Its description, technologies, project name
and contributor role are each represented by exact approved variants or typed
fields with a project-specific scope. Entity display names alone are never
rendered as claims. Every variant remains subject/scope-bound and is validated
by the existing TASK-003 graph checks; an ID alone never authorizes text.

Document plans gain typed experience claim lines that reference exact fact or
variant revisions and identify their allowed record kind/scope. Compilation
orders employment chronologically, then responsibility and linked-project
claims by explicit stable IDs; standalone projects use the same deterministic
key and never become employers. Unknown project starts sort before known starts
using a documented `(unknown, stable-id)` key, and unknown ends never become
ongoing. `compile_baseline`, `render_text`, `build_pdf`, the CLI, QA and
snapshot validation all receive and forward one explicit support-capture map;
missing or changed required captures fail closed at each boundary.

The profile schema remains `1.0` with new collections optional for backward
compatibility; the document plan remains `1.0` because its new claim-line
fields are additive and strictly validated. Existing 1.0 records load without
projects/responsibilities. A future incompatible field or semantic change must
bump the schema/plan version and provide an explicit migration; no silent
reinterpretation of old records is allowed.

No automatic prose generation, date inference, renderer change, or relaxed
approval rule is introduced. Existing stale, revoked, wrong-scope and missing
capture failures remain mandatory.

## Consequences and limits

The profile JSON Schema and plan version require a controlled schema amendment;
old revisions remain readable through explicit migration-free optional
collections. The document plan stays renderer-independent. The production
renderer still emits only validated literal text. This change proves internal
support integrity and exact preservation, not the real-world truth of prose.

## Review gate

Independent architectural review must confirm that the record shapes,
exact revision-bound subject/employment/project scopes, variant placement,
version policy, ordering and capture forwarding satisfy ADR-011, ADR-012,
ADR-013 and M1-FIX-001 before code changes are implemented. If rejected, this
task remains blocked and the proposal is revised without weakening existing
validation.
