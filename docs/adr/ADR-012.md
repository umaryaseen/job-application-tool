# ADR-012: Immutable snapshots and approvals

- Date: 2026-09-08
- Status: **ACCEPTED FOR PLANNING**
- Decision owner: supervising engineer; independent review recorded in `../reviews/`.

## Context and research disagreement

R1 1010–1058; R2 357, 497–527; R3 494–539, 667–674.

## Alternatives

Mutable application row with approved Boolean; immutable snapshots plus separate review/events; Git for all applicant data.

## Recommendation / decision

Keep private immutable snapshot directories with exact source slice, plan, output bytes, QA and hashes. Fact/wording approval is distinct from final artifact approval. Bind review to the manifest/output digests. Tracking events reference snapshot IDs; do not rewrite old artifacts.

## Trade-offs and consequences

More files and explicit state are required, but the system can identify exactly what was sent. A Boolean survives edits incorrectly. Git is for code/plans/synthetic fixtures, not applicant artifacts. Hashes detect changes; they are not encryption or protection against a malicious local OS owner.

## Validation and adoption gate

TASK-008 covers atomic staging/finalization, no overwrite, interrupted builds, stale approval, modified PDFs/support captures, source correction/supersession/revocation/deletion, unavailable eligibility and time expiry between approval and export. Export uses current time, not the build as-of date. ARCHITECTURE's eligibility matrix distinguishes loss of required source records/captures from loss of an external original whose intact reviewed capture remains active. Historical artifacts persist. Manifest hashing excludes approval records and self-referential fields. TASK-023 adds transactional events.

## Reconsideration

Revisit signing/multi-user authorization only when a new trust boundary justifies it. Preserve historical approvals but block new export after relevant revocation.
