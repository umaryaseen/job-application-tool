# ADR-018: Applicant-facing baseline presentation projection

- Date: 2026-09-15
- Status: **PROPOSED — INDEPENDENT ARCHITECTURE REVIEW REQUIRED**
- Decision owner: supervising engineer; implementation remains unapproved.

## Context

The validated M1 plan contains exact claim lines, but the initial applicant
projection exposed renderer-oriented metadata (`status: unknown` and opaque
date placeholders), flattened contact claims, and did not separate linked and
standalone projects visually. Confirmed thesis/coursework and skill categories
also need typed representation before they can be displayed; strings must not
be injected directly into a renderer.

## Proposed decision

Add a deterministic presentation projection after document-plan validation and
before both UTF-8 text and the trusted PDF token boundary. It preserves every
validated claim while applying only fixed layout rules:

- render the bound name prominently and keep other contact values in one
  labelled compact line;
- render employment title/employer and dates as separate readable lines,
  responsibilities as bullets, and linked projects once with their approved
  complete description when it already contains the typed identity/role/date;
- insert a static `Standalone Projects` marker before projects with no
  employment reference; never infer an employment relationship;
- group skills only by an explicit optional `SkillFact.category` matching one
  of the fixed labels `Data processing & analysis`, `Databases & backend`,
  `Visualization & frontend`, `AI & retrieval`, `Tools & infrastructure`.
  Preserve distinct fact IDs/revisions even when names are equal, exact
  context/proficiency and nonempty notes; unrecognized categories stay ungrouped;
- omit unknown status/date labels from display while retaining unknown values in
  canonical records. A known start with unknown end displays `Start: <date>`;
  a known end with unknown start displays `End: <date>`; wholly unknown periods
  display no date. Known ongoing periods retain `ongoing`. Known degree status
  remains visible; unknown degree names are omitted without omitting the program;
- add optional thesis title/description/coursework fields to `EducationFact`
  for future reviewed records. Existing records without these fields remain
  semantically unchanged and require no automatic migration. Empty new optional
  fields are omitted from revision digests so existing approval hashes stay
  valid. Nonempty additions are hashed and require a new reviewed revision.

The canonical fact payload (including this empty-field rule) is shared by
`fact_digest`, local review receipts and the profile digest. Presentation policy
version is part of the trusted template/build identity; changing it invalidates
new artifact approval without rewriting archived bytes.

The projection cannot change plan validation, claim wording, support bindings,
or fact status. Static markers (`Project:`, `Standalone Projects`, `Thesis:`,
`Coursework:`, `Start:`, `End:` and category headings) are fixed allowlisted labels. Candidate
text remains escaped literal token data in the PDF worker.

Project description text is always verbatim. A description replaces a metadata
header only when it contains every nonempty typed name, role, formatted period
and technology value. Partial overlap is not a license to edit approved prose:
retain the complete header, technologies and description. If that duplicates
some words, a separately approved concise canonical wording is needed; never
trim arbitrary prose. Duplicate complete metadata is rendered once.

## Consequences and limits

Presentation changes are measured by the same Poppler/pypdf complete-content
QA against an independently authored oracle. Group labels and omitted unknown
metadata are display policy, not evidence or approval. Existing approved
profiles that need thesis/coursework/category display require a normal reviewed
profile revision; this task does not manufacture those receipts or regenerate
personal outputs. The existing one-to-two-page A4 and 11 pt body contract stays
in force; overflow remains a review gate.

## Review gate

Independent architecture review must confirm that additive typed fields,
display-only omission of unknown metadata, project de-duplication conditions,
skill grouping and static markers preserve ADR-011, ADR-013, ADR-015, ADR-017
and the provenance invariant. If rejected, keep the current flat projection and
revise this proposal without weakening validation.

## 2026-09-21 amendment — M1-FIX-004

**Design approved for implementation by the supervising user. Independent
implementation review remains required.** This amends display policy only;
prior decisions and approval history above are retained.

The bound name becomes the dominant body heading without a visible Contact
label. Contacts remain literal body text; short values may be compacted,
while each complete URL stays on its own line. Required identity QA still
resolves the exact name from trusted profile/review state. Only Contact may
have no visible section heading; other standard headings remain mandatory
when their corresponding content is selected.

Use left body alignment with effective theme-level no-hyphenation, A4, 11 pt
body and 20 mm margins. Emphasize role/employer headings; use hanging bullets
and keep headings with their first associated content. Linked projects retain
the exact validated employment ID/revision and appear indented beneath it.
They never become employers. Standalone projects stay in validated plan order
under Selected Projects (replacing Standalone Projects), followed by Education,
Skills and Languages. Association-only projects gain no employment/date claim.

Page composition is content-aware: Selected Projects starts a new page only
when there is preceding content and selected standalone project content; a
weak page break cannot add a blank page. The intended two-page fixture begins
Selected Projects on page 2. Absent projects add neither heading nor break.
Excess content is preserved and causes page-limit QA failure; no shrinking,
silent omissions, overflow concealment or claim pruning is allowed.

Only redundant degree status is suppressed: an ongoing date range need not
repeat `(ongoing)`, but ongoing status remains visible when the period does
not already express it. Completed/withdrawn/unknown semantics and original
date precision remain unchanged.

Styles, indentation and page-break markers are private derived presentation
values after existing plan/provenance/placement validation. They are not
accepted in caller-supplied DocumentPlans and cannot conceal claims or change
relationships. Candidate text remains escaped literal data, including names;
placeholder-like candidate text is never interpreted as a layout command.

The new identity is `baseline-v3-presentation-m1-fix004`. New PDFs/TXT and QA
require new byte-bound review; archived artifacts, canonical facts and valid
fact approvals remain unchanged. Historical QA/final approvals cannot be
transferred to changed bytes. No second renderer or new dependency is added.

## 2026-09-22 amendment — M1-FIX-004 F-01 correction

**Pending independent implementation review.** The review of the initial
M1-FIX-004 implementation found that a long URL in the RenderCV headline was
visually readable but split at an explicit URL hyphen by PDF extraction. The
trusted PDF boundary now emits each contact scalar as its own non-breakable
block and measures each complete `Url:` line with the effective fixed Raleway
11 pt theme inside the A4 content width. A URL that fits must remain complete
under both Poppler and pypdf; a URL wider than that content width fails the
build with a bounded actionable diagnostic before a PDF is published. The
canonical URL, narrow extraction normalization, identity/provenance bindings,
font size, margins and page policy are unchanged. Changed PDF bytes require
fresh QA and byte-bound review; earlier artifact approvals do not transfer.
The corrective template identity is `baseline-v3-presentation-m1-fix004-f01`.
